# Динамические сутки, каскадные тени и voxel GI

Реализовано поверх `c883729`, Windows x64 / C++23 / Vulkan 1.3. Свет реагирует
на время, появление, удаление и перемещение объектов. Аппаратные RT extensions
не используются. Voxel GI выполняет программную трассировку по сетке на GPU;
это первый ограниченный вариант diffuse GI, а не полный аналог SVOGI CryEngine.

## Запуск и управление

По умолчанию включены динамическое освещение, voxel GI и цикл суток длиной
600 реальных секунд, начальное время 14:00. Примеры из корня репозитория:

```bat
scripts\run_windows.cmd --lighting dynamic --gi voxel --day-length 600
scripts\run_windows.cmd --lighting dynamic --gi off
scripts\run_windows.cmd --lighting legacy
scripts\run_windows.cmd --lighting-room --time-of-day 12 --day-cycle off --camera-z 4 --gi-extent 48
```

| Параметр | Допустимые значения | По умолчанию |
| --- | --- | --- |
| `--lighting` | `dynamic`, `legacy` | `dynamic` |
| `--gi` | `voxel`, `off` | `voxel` |
| `--day-cycle` | `on`, `off` | `on` |
| `--time-of-day` | часы от 0 включительно до 24 | 14 |
| `--day-length` | 1–864000 реальных секунд | 600 |
| `--gi-extent` | 16–256 единиц мира, ширина объёма | 64 |
| `--gi-strength` | 0–4, множитель отражённого солнечного света | 1 |
| `--gi-triangle-budget` | 1024–262144 треугольника на кадр | 65536 |
| `--gi-update-hz` | 1–120, частота GI при движении и обновления солнечного света | 30 |

`legacy` отключает новый свет и GI. При старте с `--gi off` тяжёлые GI-ресурсы
не создаются, compute-проходы не записываются, GI-код исключён из графических
pipelines через specialization constant. Включить GI в таком процессе нельзя:
для этого нужен запуск с `--gi voxel`. Если GI был выделен при запуске, его
можно выключать и включать в редакторе и MCP без создания GPU objects.

Панель renderer редактора содержит часы, скорость суток, паузу, GI и его
интенсивность. C++ использует `LightingSettings`, `set_lighting_settings()` и
существующий `set_runtime_transform()` / scene snapshot API. Параметры света
пока не сохраняются в scene-файл. `--lighting-room` предназначен для игрового
executable и проверки, а не для загрузки комнаты в редакторе.

MCP:

- `lighting.set {"hour":12,"cycle":false,"gi":true}`;
- `test.set_roof {"enabled":false}` — реальное удаление узла крыши, только
  в `--lighting-room`; `true` создаёт новый узел с новой generation;
- `debug.get_state.render.lighting` — состояние и счётчики;
- `debug.get_metrics` — GPU timings отдельных проходов.

## Архитектура и стоимость

1. C++ вычисляет направление, цвет и интенсивность солнца, аналитический цвет
   неба. Ночь не использует дневную HDR-панораму со статичным солнцем.
2. Растровая shadow atlas 2048² содержит четыре каскада 1024². Границы:
   12, 32, 80, 192 единицы; последние 10% диапазона смешиваются. Проекция
   привязана к texel grid. Солнце для теней округляется до 15 игровых секунд,
   прямой свет меняется непрерывно. При неизменных камере/солнце кешируются
   и матрицы, и atlas. Перемещение caster инвалидирует тени.
3. Геометрия GI — локальные треугольники shared mesh cache. Instances передают
   transform, диапазон треугольников и diffuse albedo. Terrain использует
   реальные треугольники heightfield с той же диагональю, что и raster mesh.
4. `VoxelSceneTracker` сравнивает стабильные ID/generation/mesh ranges,
   transforms и материалы. Старые и новые AABB помечают изменённые bricks;
   удаление очищает старое место. Затем все пересекающие область поверхности
   повторно записывают её. Неизменные области сохраняются. World-space AABB
   кешируются отдельно в contiguous массиве; поиск кандидатов не пересчитывает
   transforms всех объектов.
5. Сетка 64³, bricks 8³. Compute консервативно вокселизирует треугольники,
   atomics выбирают согласованную пару normal/albedo. Задание замораживает
   transforms, обрабатывается по бюджету между кадрами и не хранит borrowed
   scene pointers. Изменения во время обработки накапливаются для следующего
   задания. Радианс обновляется после завершения задания; до этого материалы
   читают предыдущую готовую текстуру. Движение объединяется в задания с частотой
   `--gi-update-hz`: по умолчанию ожидание до примерно 33 мс плюс время обработки
   задания. Появление/удаление объектов и перенос объёма имеют приоритет;
   начатое задание продолжает обрабатываться каждый кадр. Прямые тени этим
   ограничением не затрагиваются.
6. Солнечный свет инъецируется отдельно от геометрии. Его voxel DDA учитывает
   препятствия и за камерой. Radiance RGBA16F получает цепочку 3D mipmaps;
   материалы выбирают один diffuse bounce пятью конусами, максимум 14 шагов
   на конус. Небо проходит по незакрытым направлениям. GI не обновляется
   повторно при статичных источниках и геометрии.
7. Линейный HDR сохраняется до финального вывода. Fixed-exposure Reinhard
   выполняется после SMAA/FSR; sRGB attachment кодирует сигнал один раз.
   Режим без AA также использует HDR target и финальный проход.

Ресурсы выделяются заранее и переиспользуются по frame ownership. Новые
shader layouts/compute pipelines/volume views имеют RAII; upload/readback
следуют существующим fence/queue правилам. Нет нового queue idle, forced
query wait или per-frame resource creation. Query results читаются после
завершения соответствующего frame fence.

Сетка surfaces занимает 1 MiB, radiance с mipmaps около 2.29 MiB. Shared mesh
cache выделяет до 1 млн треугольников (45.78 MiB); jobs двух кадров — около
15.26 MiB. CPU vectors также ограничены и зарезервированы заранее. Cache
живёт до shutdown, не является системой streaming/eviction мешей. На
загрузке ассета staging budget включает отдельное выравнивание каждого
submesh. Limits/format support проверяются до использования GI.

`average_gpu_voxel_geometry_ms` и `average_gpu_voxel_light_ms` в benchmark JSON
усредняются по всем измеренным кадрам, включая нулевую стоимость кешированных
кадров. Выборка GI входит в `average_gpu_geometry_ms`. Счётчики geometry/radiance
updates имеют суффикс `_total`: они включают initialization и warmup.
`pending_bricks` суммирует активную и следующую очереди, включая пересечения.
`oldest_geometry_ms` — консервативная оценка: при непрерывных изменениях во
время многокадрового задания она показывает возраст незавершённого цикла
обновлений, а не точную задержку каждого voxel.

## Ограничения этого варианта

- Один объём вокруг камеры, без clipmaps. Перенос объёма требует полного
  обновления его геометрии. На границе используется переход к sky ambient.
- Один diffuse bounce солнечного света; нет многократных отражений, GI от
  emissive/локальных ламп, voxel specular reflections и физической атмосферы.
- Геометрия и препятствия за пределами объёма не участвуют в voxel GI.
  Солнечные растровые тени ограничены дальностью каскадов.
- Малые детали и стены тоньше voxel могут терять контактные тени или давать
  утечки света. По умолчанию voxel равен одной единице мира. Normal и albedo
  представлены одной поверхностью на voxel; текстуры моделей усредняются
  по ограниченной выборке. Это приближение, не точный light transport.
- Бюджет треугольников ограничивает объём задания, но не гарантирует одинаковые
  миллисекунды на разных GPU и для треугольников разной площади. Сбор кандидатов
  при старте задания всё ещё сканирует кешированные AABB всех поверхностей.
  Задержка видна в
  `pending_bricks` / `oldest_geometry_ms`.
- Каждый обновляемый shadow cascade пока рисует все группы caster-ов.
  Отдельная GPU-компактизация shadow casters и shadow LOD ещё не реализованы.
- Изменения мира проходят через C++ scene/runtime API. Это не симулятор
  разрушения, не редактирование уже загруженных vertex buffers на месте и
  не deformable/skinned GI. Загрузка нового asset добавляет его треугольники
  в общий cache.
- Bake/lightmap/light-probe backend и интерполяция запечённых состояний суток
  остаются отдельной задачей. `--gi off` означает динамический direct light
  и sky ambient, а не запечённое GI.

## Проверка

Windows Debug, Release и MSVC ASan: по шесть наборов CTest. Новые CPU-тесты
проверяют сутки, bounds/cascade coverage, seams bricks, удаления после runtime
перемещения, reused generations, материалы и несколько submesh одного объекта.

```powershell
.\scripts\render_validation_windows.ps1 -ExePath .\build\windows-debug\bin\vulkan_cube.exe -Scenario lighting
.\scripts\render_validation_windows.ps1 -ExePath .\build\windows-asan\bin\vulkan_cube.exe -Scenario lighting
.\scripts\lighting_submesh_validation_windows.ps1 -ExePath .\build\windows-debug\bin\vulkan_cube.exe
```

Проверочная комната: фиксированные noon/night/dawn, удаление/восстановление
крыши, GI off/on, выход камеры из старого voxel-объёма. Сравниваются счётчики
и pixels: затенённый объект реагирует на GI и проём, ночь темнее, восстановление
крыши возвращает побитово исходную картинку. Затем resize, IMMEDIATE/FIFO,
Off/SMAA/FSR, instancing и compute workload, shutdown.

Дополнительно выполнены canonical/animated/stress/streaming сценарии: по три
startup/shutdown и два цикла переключений в Debug и ASan, всего 30 запусков
и 300 captures переключений, плюс 36 фиксированных кадров комнаты. Vulkan synchronization validation и live VMA
allocation checks включены. Ошибок этих проверок не обнаружено.

После ограничения частоты GI повторены lighting/stress/streaming в Debug и
ASan: ещё 18 startup/shutdown. В stress тест проверяет реальную частоту
изменения геометрии: 12–13 завершённых заданий за 0.41–0.45 секунды. Отдельная
синтетическая модель из 32 submeshes проверяет staging alignment в Debug/ASan.
После уточнения shadow barriers повторены lighting/stress в обеих конфигурациях.

Native clang-tidy выполнен для 12 затронутых translation units, MSVC Core Check
для шести; последние изменения lighting/upload проверены повторно. Новых
подтверждённых lifetime/bounds/race дефектов не осталось.
Анализаторы не являются warning-free: общие предупреждения о Vulkan flag typedefs,
проверенных индексах массивов, стилевых conversions и ранее существующем optional
под mutex разобраны вручную. RGP/PIX hardware-counter capture и глобальный heap
allocation profiler не запускались. Отсутствие per-frame allocation в новом коде
проверено по ownership/capacity; это не измерение всех аллокаций зависимостей.

## Сопоставимые замеры

Методика: RX 6800, Ryzen 7 9700X, драйвер 32.0.21045.5002, нативный Release,
1920×1080, IMMEDIATE, AA off, 5 секунд прогрева + 15 секунд измерения, три
чередующихся прогона. Clocks/температура не фиксировались; power scheme и
фоновые процессы записаны рядом с JSON. Старый executable `c883729` запускался
с собственными shaders/runtime DLL и теми же неизменёнными project assets.

Команды для повторения:

```powershell
.\scripts\benchmark_evolution_windows.ps1 -Suite Lighting -BaselineExe <baseline.exe> -OutputName lighting-comparison
.\scripts\benchmark_evolution_windows.ps1 -Suite LightingStress -OutputName lighting-stress
```

Медианы трёх прогонов итоговой сборки; диапазон — минимум/максимум среднего
FPS отдельных прогонов. Canonical scene содержит 17 source instances и
119009 отправленных треугольников. Это другая нагрузка и разрешение, чем
исходная контрольная сцена 1280×720 со 170 треугольниками.

| Canonical, 1920×1080 | FPS | Диапазон FPS | 1% low | CPU frame, мс | GPU frame, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| Старая сборка `c883729` | 3206.5 | 3035.5–3459.0 | 1305.2 | 0.3119 | 0.1602 |
| Итоговая, `--lighting legacy` | 3335.4 | 3052.8–3363.7 | 1450.1 | 0.2998 | 0.1599 |
| Динамические сутки + CSM, `--gi off` | 2935.0 | 2792.6–2941.8 | 1437.3 | 0.3407 | 0.1997 |
| Динамические сутки + CSM + voxel GI | 845.9 | 843.2–848.9 | 753.3 | 1.1822 | 0.9984 |

Устойчивой регрессии legacy не обнаружено: диапазоны перекрываются, GPU time
практически совпадает. Прирост медианы FPS нельзя приписывать оптимизации:
старый executable в предыдущей серии давал медиану 2624.5 FPS при тех же
аргументах. Поэтому итоговая таблица использует заново чередовавшиеся old/new
запуски, а не смешивает лучшие результаты разных серий.

Динамическое освещение без GI добавляет около 0.040 мс GPU относительно legacy:
работают CSM и HDR с финальным tone mapping. В итоговой серии медиана FPS ниже
старой сборки на 8.5%; это цена новых проходов, которую нельзя выдавать за
«освещение без потери FPS». Voxel GI добавляет ещё около 0.799 мс GPU. Основная
стоимость — выборка конусов в geometry pass (0.964 мс с GI против 0.169 мс без
GI). Сам relight в среднем занимает 0.0015 мс на кадр. У статичной геометрии
после прогрева нет повторной вокселизации.

CPU frame включает ожидание внутри `present` и не равен времени полезных CPU
вычислений. Для canonical с GI медиана `scene_prepare` — 0.00135 мс, тогда как
`present` занимает 1.055 мс.

Stress: 100000 source instances, одна анимированная стена и движущаяся камера.

| Stress, 1920×1080 | FPS | Диапазон FPS | 1% low | CPU frame, мс | GPU frame, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| Динамические сутки + CSM, GI off | 1004.7 | 998.5–1005.9 | 859.6 | 0.9953 | 0.8251 |
| Динамические сутки + CSM + voxel GI | 678.2 | 676.4–679.2 | 531.0 | 1.4745 | 1.3011 |

В промежуточном варианте движение стены запускало GI на каждом render frame,
а сбор кандидатов заново вычислял world bounds всех поверхностей. После
кеширования AABB и ограничения частоты получены следующие медианы трёх
прогонов с одинаковыми scene/camera параметрами:

| Stress с voxel GI | До ограничения частоты | Итоговый вариант |
| --- | ---: | ---: |
| FPS | 534.9 | 678.2 (+26.8%) |
| CPU scene preparation, мс/кадр | 1.0118 | 0.0446 |
| GPU frame, мс | 1.6592 | 1.3011 |
| GPU voxel geometry, мс/кадр | 0.3343 | 0.0145 |
| GPU voxel relight, мс/кадр | 0.0365 | 0.0016 |

Это выигрыш от устранения лишней работы с явно изменённой частотой GI, а не
ускорение идентичного числа voxel dispatches. Прямые тени сохраняют свою
частоту. В двадцатисекундном итоговом запуске выполнено около 588 GI updates.
В stress основная оставшаяся стоимость — geometry pass с выборкой GI
(0.653 мс) и тени (0.570 мс). Для дальнейшего ускорения нужно сначала проверять
shadow caster culling/LOD и выборку GI в меньшем разрешении с восстановлением
по depth/normal. Выигрыш этих следующих изменений пока не измерен.
